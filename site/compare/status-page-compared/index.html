Deploy status page: static file or hosted status service

Deploy Center's status page is a static snapshot of what shipped when, made from your deploy history and hosted anywhere. A hosted status service is built for incidents, subscribers and uptime. They answer different questions, and you can run both.

When to use which

  • Customers or a team ask "did the fix go out?": the deploy page answers that without anyone writing an update. See set up a status page for your deploys.
  • Customers ask "is it down?": you need monitoring and incident posts, which a deploy snapshot does not provide.
  • Both: keep the deploy page for what shipped and link to your incident page from it.

Honest limit. The deploy page is as fresh as the last time the script ran and the folder was uploaded. If the job stops, a red line with the page's age appears after staleHours (default 48), which only shows with scripts enabled in the browser.

Questions

Can the deploy page replace a hosted status service?

Only if all you need is a record of what shipped. It has no uptime monitoring and no subscriber emails.

Is it safe to publish?

With strict on, the page hides commit messages, moves its script into a separate file for a strict content policy and carries noindex. Only the projects you list are shown.

Do I need a server?

No. It is three static files that any static host serves.

Can other tools read it?

Yes. status.json has the same data and a schema number.

Use Vercel or Render too?

Deploy Center turns off auto-deploy on Vercel and Render in one click, Netlify and other hosts opt-in, and deploys what changed when you decide. Free and open source for macOS.
