Deploy only when CI is green

Run deploys deploy-changed --when-green --yes. For each project it reads the head commit's checks, waits while they run, skips the project if they failed, and, on hosts that can deploy a given commit, deploys exactly the commit it checked.

Last updated 20 November 2026 · by Patrick Schmetzer, author of Deploy Center

Deutsche Fassung

1. Turn it on for a deploy

deploys deploy-changed --when-green --yes
deploys deploy-changed --when-green --wait 45m --yes --json   # one JSON record per project

Without --yes it only shows what it would deploy. The CLI reads the combined status and the check runs of the head commit through gh api, so gh has to be logged in.

2. What each CI state does

CIWhat happens
green (passed, skipped or neutral)deployed, at exactly that commit where the host can deploy a given commit
no checks at alldeployed, since there is nothing to wait for
pending (queued or running)asked again after 10 s, 20 s, 40 s and so on (at most 2 minutes apart), up to --wait (default 30m)
red (failure, timeout, cancel, action required)skipped, with the checks that failed
GitHub not reachabletreated like pending; skipped once --wait runs out

Projects are checked in rounds, so one slow CI does not hold up the others. A push that lands during the wait goes out in the next run, not unchecked in this one.

3. Two settings

  • DEPLOYS_CI_GRACE (default 90 seconds): a commit younger than that with no check yet counts as "CI has not started", which is pending, not "no checks". Raise it for slow runners.
  • DEPLOYS_CI_IGNORE: a regular expression for check names that do not count, for an optional check that is always red, for example DEPLOYS_CI_IGNORE='^(codecov|lint-optional)'. Without it one such check holds every deploy back.

4. Ask about one commit

deploys ci owner/repo <sha-or-branch> --wait 10m

Exit code 0 means green or no checks, 1 means red, and 2 means checks are still pending or GitHub is not reachable. With --json the exit code is always 0 and the verdict is in the answer, which suits a script that decides for itself.

In the app a red CI does not hold a deploy back. The row shows "CI is red" with the failed checks, and Deploy starts anyway. The rule above is for the CLI, CI jobs and scheduled deploys.

5. On the host instead

Render has the same idea built in: set Auto-Deploy to After CI Checks Pass and a push whose checks fail does not deploy. That keeps auto-deploy on; --when-green keeps the decision with you. See Render auto-deploy.

Questions

Does --when-green deploy a project without any CI?

Yes. With no checks at all there is nothing to wait for, so it deploys. A commit younger than DEPLOYS_CI_GRACE seconds with no check yet counts as pending instead.

What if an optional check is always red?

Set DEPLOYS_CI_IGNORE to a regular expression for its name so it does not hold every deploy back.

Which commit is deployed?

The commit that was checked (--sha), on hosts that can deploy a given commit, such as Vercel, Render and AWS Amplify. Netlify and Cloudflare Pages cannot, so a build there starts from the newest commit of the branch, which can be newer than the one checked. On the others, a newer push goes out in the next run.

Does it work in CI or a scheduled job?

Yes. Combine it with a schedule, see a daily deploy, and give the job a GH_TOKEN.
