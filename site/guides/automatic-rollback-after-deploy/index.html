Roll back automatically when a deploy breaks the site

Run deploys verify <project> --path /health after a deploy. It asks the site three times and, if all three answers are 5xx or nothing, counts down 10 seconds and rolls production back, unless you press Ctrl-C or pass --no-rollback.

Last updated 20 November 2026 · by Patrick Schmetzer, author of Deploy Center

Deutsche Fassung

1. Run the check after a deploy

deploys deploy web && deploys verify web --path /api/health

verify first waits until the newest production deploy is live. If that deploy failed, there is nothing to check. Then it requests the site, plus --path if you give one, three times, five seconds apart. Redirects are followed.

2. What counts as broken

  • The check fails only when all three answers are 5xx or nothing at all (a timeout or no connection). A fresh Render service can answer 502 for a few seconds, which is why one bad answer is not enough.
  • Without --path, a 4xx is not a failure: it usually means a protected page, and a rollback would not fix that.
  • With --path, the address must exist. A 4xx there, for example a missing /health, counts as a failure.

Pick a path that touches what matters: your health route, or a page that reads from the database.

3. Exit codes for scripts and CI

ExitMeaning
0healthy
1the check failed and production was rolled back
2the check failed and nothing was rolled back (--no-rollback, Ctrl-C, or the rollback failed)
3nothing was checked: unknown project, the newest deploy is not live, no address, a wrong option

The rollback, or the stopped rollback, is written to the journal.

4. In the app

Open a project's details and tick Roll back if the check fails. It is set per project and kept on this Mac. A 5xx or no answer then starts a 10-second countdown, shown as a notification and as a line in the window, both with Cancel. A 404 does not start a rollback, and neither does the check after a rollback.

What a rollback does not undo. It points production at an earlier deployment. Database migrations and changed environment variables stay as they are, so look at what a deploy would ship before you deploy. Rollback and verify are still allowed inside a deploy freeze, because a rollback is a fix.

Questions

Does verify roll back on every host?

The automatic rollback is built for Vercel and Render projects. On other hosts a rollback is a separate command, deploys <host> rollback <project>; a plain deploy hook has no rollback. See the host table in the docs.

Can I only report and never roll back?

Yes. Pass --no-rollback and verify only reports, with exit code 2 when the check fails.

What if the site is slow but not down?

A slow answer is not a failure for verify. The app's "Watch the site after going live" setting keeps asking for a few minutes and says when the site answers slower than before the deploy.

Is a rollback a deploy for the deploy freeze?

No. Previews, rollbacks and verify are not stopped by the deploy window.
