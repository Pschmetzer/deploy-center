Monorepo ignore rules: build only the app that changed

In a monorepo one push builds every connected project, even if only one folder changed. Give each project a rule that compares its own folders and the shared packages it uses: a skip setting or Ignored Build Step on Vercel, an ignore command on Netlify, Build Filters on Render, build watch paths on Cloudflare Pages.

Last updated 27 November 2026 · by Patrick Schmetzer, author of Deploy Center

Deutsche Fassung

1. Why one push builds everything

Each project in your host connects to the same repository, and each one builds on a push. A web app, a docs site and an admin app in one repository build three times when only the docs changed. A rule per project tells the host which folders matter to it.

2. Vercel

Three options, from least to most work:

  • With npm, yarn or pnpm workspaces, turn on the setting that skips a deployment when the project's root directory and its dependencies did not change (build settings, under Root Directory).
  • With Turborepo, set the Ignored Build Step to npx turbo-ignore.
  • Otherwise compare the folders yourself:
git diff --quiet HEAD^ HEAD -- . ../../packages/ui

Exit 0 means nothing changed, so Vercel skips the build. HEAD^ only looks at the newest commit of a push; the Ignored Build Step guide has a script that compares with the last deployment instead.

3. Netlify

Netlify sets CACHED_COMMIT_REF (the commit of the last build) and COMMIT_REF (the commit being built). Compare the folders between them:

# netlify.toml, in the site's folder
[build]
  ignore = "bash scripts/netlify-ignore.sh"
#!/usr/bin/env bash
# scripts/netlify-ignore.sh  -  exit 0 = skip the build, exit 1 = build
[ -n "${CACHED_COMMIT_REF:-}" ] || exit 1                 # no earlier build: build
[ "$CACHED_COMMIT_REF" != "$COMMIT_REF" ] || exit 1       # nothing to compare with: build
git diff --quiet "$CACHED_COMMIT_REF" "$COMMIT_REF" -- . ../../packages/ui

The first two lines matter: when there is no cached build to compare with, the two references can be missing or equal, and git diff of a commit with itself would exit 0 and cancel the build. A command that errors also exits non-zero and Netlify builds, which is the safe direction.

4. Render

In the service's Settings → Build & Deploy use Build Filters: paths to include and paths to ignore. A change outside the included paths does not deploy. List the shared packages the service imports as included paths, or it will miss a change that affects it.

5. Cloudflare Pages

Open Settings → Builds & deployments and look for build watch paths, where you list the paths that should start a build and the ones that should not. If your project does not show them, use one Pages project per app with production deployments set as in the Cloudflare Pages guide.

6. Pitfalls

  • Shared code. A change in packages/ui must build every app that imports it. List shared folders in each rule.
  • Root files. A changed lockfile, a root config or a CI file can affect every app. Decide whether they count.
  • A skipped build is not a deploy. The host cancels it, so production stays on the last build. Check that a real change still builds.
  • Test the rule. Run it locally and print the exit code before you rely on it.

When rules are too much. If production should simply go live when you decide, turning auto-deploy off is one switch per project instead of one rule per project.

7. What Deploy Center adds

deploys changed counts the commits waiting per project from the repository's history, and deploys explain <project> says why a project is or is not counted as changed. They show what waits to be deployed; they do not apply your host's path rules, so a docs-only push can still list several projects. To check a rule, look at the host's own build list after a push: the projects it should skip show a cancelled or skipped build.

Questions

Does one rule work for all hosts?

No. Each host reads its own setting, with the same idea: compare the folders a project depends on with the last build.

Why does Vercel still build after I added git diff?

Most often the script errors, or HEAD^ only looked at the newest commit of a push with several. Run it locally and print the exit code.

What if I forget a shared package?

The project does not rebuild when only that package changes. Add the package folder to the rule and keep the list in one script that you review.

Is turning auto-deploy off simpler?

Often. One setting per project replaces a rule per project, and you deploy what changed when you decide.
