Deploy to Vercel from GitHub Actions: label or schedule

Turn off Git auto-deploy, then let a workflow deploy when you decide: a deploy hook called when a pull request with the label deploy is merged, a prebuilt deploy with the Vercel CLI, or a daily job that deploys only the projects that changed.

Last updated 23 November 2026 · by Patrick Schmetzer, author of Deploy Center

With Git auto-deploy on, every push builds. A workflow gives you the same automation on a rule you choose. Pick one of three.

1. A deploy hook on a label

Create a deploy hook in Project → Settings → Git → Deploy Hooks and store its URL as a secret named VERCEL_DEPLOY_HOOK. A hook always builds the newest commit of its branch.

name: Deploy on label
on:
  pull_request:
    types: [closed, labeled]
permissions: {}
jobs:
  deploy:
    if: >-
      github.event.pull_request.merged == true &&
      ((github.event.action == 'closed' && contains(github.event.pull_request.labels.*.name, 'deploy')) ||
       (github.event.action == 'labeled' && github.event.label.name == 'deploy'))
    runs-on: ubuntu-latest
    steps:
      - env:
          HOOK: ${{ secrets.VERCEL_DEPLOY_HOOK }}
        run: curl -fsS --retry 3 --retry-all-errors -X POST "$HOOK"

A merged pull request with the label deploy starts one build. Other merges cost nothing. The hook URL is a secret: anyone who has it can start a build.

2. A prebuilt deploy with the Vercel CLI

Build in the runner and upload the result, so Vercel does not build at all. The token is a secret named VERCEL_TOKEN; pin the CLI version you tested.

npm install -g vercel@VERSION
vercel pull --yes --environment=production --token "$VERCEL_TOKEN"
vercel build --prod --token "$VERCEL_TOKEN"
vercel deploy --prebuilt --prod --token "$VERCEL_TOKEN"

3. One daily deploy of what changed

Deploy Center's example workflow installs the deploys CLI from the release tarball, checks it against the release's checksums.txt, and runs deploys deploy-changed --yes on a schedule, with a dry run for the first try. It needs VERCEL_TOKEN, a GitHub token that can read your app repos, and the file vercel-repos.json, which says where each disconnected project deploys from. The workflow is examples/daily-deploy.yml.

Trade-offs. A scheduled workflow in a public repository can be switched off by GitHub after a period without activity, and a cron time is UTC. Watch the first runs, and add a step that tells you when it fails.

In Deploy Center

Deploy Center ships a GitHub Action that lists what is waiting and deploys only with deploy: true. Pin it to a release tag or a commit, never to main, because the workflow holds your deploy tokens. See install the CLI for the CI variables.

Questions

How do I deploy only when I say so?

Turn off Git auto-deploy, then call a deploy hook from a workflow when a pull request with a label is merged, or run a scheduled job that deploys only what changed.

What does vercel deploy --prebuilt do?

It uploads a build made on your machine or in the runner, so Vercel itself does not run the build.

Does a deploy hook build an old commit?

No. A Vercel deploy hook always builds the newest commit of its branch.

Which secrets do the workflows need?

VERCEL_TOKEN or the deploy hook URL, and for the daily job a GitHub token that can read your app repos.
