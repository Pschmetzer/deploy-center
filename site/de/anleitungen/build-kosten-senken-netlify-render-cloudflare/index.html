Build-Kosten bei Netlify, Render und Cloudflare Pages senken

Die Hebel sind bei jedem Anbieter gleich: weniger Builds, dann günstigere Builds. Netlify: Stop builds oder ein ignore-Befehl. Render: Auto-Deploy Off, After CI Checks Pass, Build Filters. Cloudflare Pages: Production- und Preview-Deployments abschalten, das schont auch dein monatliches Build-Limit.

Zuletzt aktualisiert am 20. November 2026 · von Patrick Schmetzer, Autor von Deploy Center

English version

1. Was diese Anleitung zählt

Preise und Tarifgrenzen ändern sich; diese Anleitung zählt deshalb Builds, nicht Euro. Was ein Build dich kostet, siehst du auf der Nutzungs- oder Abrechnungsseite deines Anbieters; mit deploys simulate oder dem Build-Kosten-Rechner schätzt du die Ersparnis mit deinen eigenen Zahlen.

2. Netlify

  • Stop builds schaltet jeden Build ab, auch Build Hooks; du deployst, indem du einen Build mit der CLI hochlädst.
  • Ein ignore-Befehl in netlify.toml bricht Builds ab, die er ablehnt. test -z "$INCOMING_HOOK_TITLE" überspringt alles außer Builds, die ein Build Hook gestartet hat.
  • Previews für Bots lassen sich mit einem Skript überspringen: Preview-Builds für Bots vermeiden.

Einzelheiten und Abwägungen: Stop Netlify builds (englisch).

3. Render

  • Auto-Deploy hat drei Einstellungen: On Commit, After CI Checks Pass und Off. After CI Checks Pass überspringt Deploys von Pushes, deren Checks fehlschlagen.
  • Build Filters (einbezogene und ignorierte Pfade) verhindern, dass eine README-Änderung deployt.
  • [skip render] in einer Commit-Nachricht überspringt diesen Commit.
  • Pull-Request-Previews sind eine eigene Einstellung.

Einzelheiten: Turn off Render auto-deploy (englisch).

4. Cloudflare Pages

Cloudflare berechnet nichts pro Build. Pages-Tarife haben ein Limit für die Zahl der Builds, und jeder Push in ein verbundenes Repository und jeder Push auf einen Preview-Branch verbraucht einen Build. Stelle Production deployments und Preview deployments auf aus, um Push-Builds zu stoppen, und prüfe mit einem echten Build, wie sich ein von Hand angelegtes Deployment verhält. Einzelheiten: Stop Cloudflare Pages builds (englisch).

5. Bei jedem Anbieter

  1. Schalte Push-Builds für Production ab und deploye einmal, wenn du bereit bist: deploys netlify autodeploy-off <site>, deploys render autodeploy-off --all, deploys cloudflare off <project>.
  2. Deploye, was sich geändert hat, mit deploys deploy-changed --yes oder nach Zeitplan mit einem täglichen Deploy.
  3. Setze eine Ausgabengrenze mit deploys budget set 50 --strict: deploy-changed --yes hält dann an, bevor es darüber geht.
  4. Lies das Ergebnis mit deploys ledger.

Abwägung. Bei abgeschalteten Push-Builds ist ein gemergter Fix erst live, wenn jemand deployt. Halte einen Deploy-Freeze und eine Rollback-Prüfung bereit, damit seltener deployen sicher bleibt.

Fragen

Welcher Anbieter ist am günstigsten?

Das hängt von deinem Tarif, deinen Builds und deinem Traffic ab und ändert sich. Diese Anleitung reiht Anbieter nicht; sie listet die Einstellungen, die bei jedem Builds senken.

Berechnet Cloudflare Pages jeden Build?

Nein. Pages-Tarife haben stattdessen ein Build-Limit pro Monat. Jeder Push in ein verbundenes Repository und jeder Preview-Branch-Push verbraucht einen Build.

Unterstützt Deploy Center alle drei?

Ja. Netlify und Cloudflare Pages sind optionale Anbieter (deploys providers enable netlify, deploys providers enable cloudflare), Render ist standardmäßig an.

Wo sehe ich, was ich gespart habe?

deploys ledger schätzt Builds und Geld, die seit dem Abschalten von Auto-Deploy gespart wurden. Es ist eine Schätzung, keine Rechnung.

Du nutzt Vercel oder Render?

Deploy Center schaltet Auto-Deploy bei Vercel und Render mit einem Klick ab, Netlify und andere Hosts sind optional, und es deployt, was sich geändert hat, wenn du es entscheidest. Kostenlos und Open Source für macOS.
