Eine Statusseite für deine Deploys einrichten

Kopiere statuspage.example.json nach statuspage.json, trage die anzuzeigenden Projekte ein und führe integrations/statuspage/statuspage.sh aus. Es schreibt index.html, feed.xml und status.json nach public/ und deployt nichts: Den Ordner lädst du bei einem beliebigen statischen Host hoch.

Zuletzt aktualisiert am 20. November 2026 · von Patrick Schmetzer, Autor von Deploy Center

English version

1. Was du bekommst

Drei Dateien, kein Server und keine externen Assets:

DateiInhalt
index.htmlEine Seite, hell und dunkel, auf dem Handy lesbar.
feed.xmlEin Atom-Feed mit einem Eintrag je Deploy in der Zeitleiste.
status.jsonDieselben Daten für andere Werkzeuge, mit schema: 1.

Für jedes Projekt zeigt die Seite Zustand und Zeit des Live-Deploys (Live, Deploying, Failed), was gemergt, aber noch nicht live ist („Coming next“), eine optionale Seitenprüfung und darunter die letzten Deploys aus dem Journal der App.

2. Schreibe die Konfiguration

{
  "title": "Acme deploys",
  "description": "What shipped when.",
  "baseUrl": "https://status.example.com/",
  "projects": [
    "app-web",
    "render/worker",
    { "name": "api", "platform": "render", "label": "API", "url": "https://api.example.com/health" }
  ],
  "hideMessages": true,
  "showAuthors": false,
  "timeline": 30
}

projects ist eine Allowlist: Nur diese werden angezeigt, in dieser Reihenfolge, und ohne sie hält das Skript an und schreibt nichts. hideMessages: true zeigt „Updated“ statt der Commit-Nachrichten, in der Seite, im Feed und in status.json.

3. Erzeuge die Seite

cp integrations/statuspage/statuspage.example.json statuspage.json   # dann bearbeiten
integrations/statuspage/statuspage.sh                  # liest ./statuspage.json, schreibt ./public/

Öffne public/index.html zuerst lokal. Lade public/ dann bei einem beliebigen statischen Host hoch: S3, Cloudflare Pages, einen Webserver mit rsync -a public/ host:/var/www/status/ oder ziehe den Ordner auf Netlify Drop. Auf dem Server läuft nichts.

4. Bevor Fremde sie sehen

  • Setze "strict": true für eine Seite, die jeder sehen darf. Es schließt hideMessages ein, verlegt das Skript der Seite nach status.js, damit eine script-src 'self'-Richtlinie hält, und setzt noindex.
  • Nie veröffentlicht werden: Projekte, die nicht in der Liste stehen, Repositories, Commit-SHAs, Fehlertexte und die URLs der Seitenprüfungen.
  • Die Seitenprüfung ruft die Adresse einmal ab, während die Seite entsteht. Sie ist das Ergebnis in diesem Moment, keine Verfügbarkeit über die Zeit.

5. Halte sie aktuell

Die Seite ist eine Momentaufnahme. Führe das Skript über launchd oder cron aus und lade danach hoch. Bleibt der Job stehen, setzt staleHours (Standard 48) eine rote Zeile auf die Seite, die sagt, wie alt sie ist.

Fragen

Deployt die Statusseite etwas?

Nein. Das Skript schreibt nur drei Dateien. Du entscheidest, wohin sie gehen.

Zeigt sie Commit-Nachrichten?

Nicht, wenn hideMessages an ist, wie in der Beispielkonfiguration. Mit strict ist es von selbst an.

Ist sie ein Uptime-Monitor?

Nein. Die optionale Seitenprüfung ist eine Anfrage, wenn die Seite entsteht. Für Verfügbarkeit über die Zeit brauchst du einen Monitor, der die Seite regelmäßig abfragt.

Können andere Werkzeuge sie lesen?

Ja. status.json hat dieselben Daten und eine schema-Nummer, damit ein Werkzeug merkt, wenn sich das Format ändert.
